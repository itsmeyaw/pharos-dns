# grpc

[CoreDNS v1.15.0 README](https://github.com/coredns/coredns/blob/v1.15.0/plugin/grpc/README.md)

## grpc

- Syntax matches CoreDNS: `grpc FROM TO... { except NAME...; tls [CERT KEY] [CA]; tls_servername NAME; policy random|round_robin|sequential; fallthrough [ZONE...] }`. The Directive is allowed once per Server Block, takes at most 15 Upstreams, and accepts a resolv.conf-style file as TO (each `nameserver` on port 53).
- TO is parsed as CoreDNS `HostPortOrFile` does: an IP address, `IP:PORT` (default port 53), `[IPV6]:PORT`, `unix://PATH`, an optional `dns://`, `tls://`, `quic://`, `grpc://`, `https://` or `https3://` prefix, or a resolv.conf-style file (each `nameserver` on port 53, its IPv6 zone dropped). What CoreDNS accepts at setup Pharos accepts too, and what grpc-go cannot dial fails the first call with SERVFAIL, not setup: any scheme except `dns://` and `unix://`, a nameserver in a file that is a host name, and a port that is not a number in 1-65535 (CoreDNS does not check the port at setup, so port 0 is accepted and its dial fails). An address without a port keeps its IPv6 zone (`fe80::1%eth0`); the zone is resolved with `getaddrinfo` when dialling, as Go does, and host names from a file are resolved the same way. A numeric port is the only form dialled; grpc-go also takes a service name such as `domain`, which fails the call here.
- A Query inside FROM and not under an `except` name goes to the Upstreams in `policy` order (default `random`; `round_robin` starts with the next Upstream on each Query). The first Upstream that answers wins; an error, a timeout or a reply that is not one DNS Message moves on to the next. One 5 second deadline covers all attempts, and is sent as `grpc-timeout`. As in CoreDNS, there is no hedging: an Upstream that hangs holds the call until the deadline, then the Query fails (or falls through) without trying the next Upstream.
- Without `tls` and `tls_servername` the call is plain-text gRPC (HTTP/2 prior knowledge). Either one turns TLS on: `tls` takes `CA`, `CERT KEY` or `CERT KEY CA` (relative paths join `root`) and no argument keeps the system roots; `tls_servername` is the name the certificate must carry, else the Upstream's IP address. TLS 1.2 is the minimum and ALPN `h2` is required, as in grpc-go. The client uses the shared `pharos_server::tls` configuration (rustls with aws-lc-rs).
- The gRPC framing and the one-field `DnsPacket` protobuf are the hand-written ones of `pharos_server::grpc`, over hyper's HTTP/2 client, without tonic or prost. Compression is not offered and a compressed reply is an error. A reply over 65539 octets, a DNS Message over 65535 octets, or more than one message in the reply is an error, as `MaxCallRecvMsgSize` is in grpc-go.
- gRPC status `NotFound` is an empty NXDOMAIN reply (Question, RD and CD copied) and is not counted in the metrics. A reply whose Question differs from the Query's, or that is not a Response, is answered with FORMERR. When every Upstream fails the Query gets SERVFAIL.
- `fallthrough` hands an NXDOMAIN reply, or the failure of every Upstream, to the next Plugin; with no next Plugin the NXDOMAIN reply is the answer and a failure is SERVFAIL.
- Each Upstream has one lazily dialled HTTP/2 connection shared by concurrent Queries. A call that fails because a reused connection had closed is sent again once on a new connection (grpc-go retries transparently too). Shutdown closes the connections.
- AD is cleared on every reply (RFC 4035 §4.6, as for `forward`'s encrypted Upstreams); CoreDNS preserves it.
- Pharos itself allocates nothing per Query once warm: the request buffer comes from a small pool and is shared with the call, `grpc-timeout` is formatted on the stack, and an NXDOMAIN kept for `fallthrough` goes to a pooled buffer. hyper, `http` and `h2` still allocate about 19 times per call (header map and values, request and response streams, response frames and trailers), so the warm path is not allocation-free. `tests/allocations/grpc_allocations.rs` pins Pharos's share to zero by comparing a warmed Query, with and without NXDOMAIN fallthrough, to a bare hyper call against the same zero-allocation stub.
- The reply must have an `application/grpc` content-type, and `grpc-status` in the initial headers is accepted only in the Trailers-Only form (no body); anything else is an Upstream error, as in grpc-go.
- Metrics `pharos_grpc_requests_total{to}`, `pharos_grpc_responses_total{rcode,to}` and `pharos_grpc_request_duration_seconds{to}` replace the `coredns_` series. A call that errors is not counted, as in CoreDNS. The `to` label is the target text CoreDNS builds (`127.0.0.1:53`, `[::1]:53`, an `IP:PORT` as written, `unix://PATH`). The response counter's help text repeats CoreDNS's ("Counter of requests made per upstream.").
- Differential scenarios are skipped: the CoreDNS reference binary has no gRPC Upstream to compare against without a shared stub, and the behaviour is pinned by the ported setup, policy and proxy tests plus the stub and `grpc_server` Listener tests in `tests/functional/grpc.rs`.
- Tracing spans are not created (the `trace` Plugin is not implemented).
