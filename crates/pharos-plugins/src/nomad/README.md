# nomad

[CoreDNS v1.15.0 README](https://github.com/coredns/coredns/blob/v1.15.0/plugin/nomad/README.md)

## nomad

- Repeated `nomad` Directives in one Server Block each build an instance, chained in Corefile order; the first whose zone holds the name answers and the Plugin is ready when all instances are. CoreDNS v1.15.0 has no once-only check either, but its `parse` reads a single `c.Next()` and so silently drops every Directive after the first; Pharos serves them.
- Syntax matches CoreDNS v1.15.0: `nomad [ZONE] { address URL...; filter FILTER; token TOKEN; ttl SECONDS }`. `ZONE` defaults to `service.nomad` and only the first argument is read. The v1.15.0 plugin has no `fallthrough` property and takes one `ZONE`, not `ZONES...` as some issue text says; `fallthrough` is rejected as an unknown property.
- Settings come from the `NOMAD_*` environment as in the Nomad Go client: `NOMAD_ADDR` (used when no `address` is set; default `http://127.0.0.1:4646`), `NOMAD_TOKEN` (a Corefile `token` wins), `NOMAD_REGION`, `NOMAD_HTTP_AUTH` (`user:password`), `NOMAD_CACERT`, `NOMAD_CLIENT_CERT` with `NOMAD_CLIENT_KEY`, `NOMAD_TLS_SERVER_NAME`. `NOMAD_SKIP_VERIFY` and `NOMAD_CAPATH` fail setup instead of being ignored. `NOMAD_NAMESPACE` is ignored: the Go client only sends it on requests that name no namespace, and the service request always names one. Addresses are `http://`, `https://` or `unix://` with no credentials or path; credentials never reach logs, errors or Debug output.
- Several `address` URLs fail over: a Query goes to the endpoint that answered last and moves on to the next one on any error. CoreDNS instead probes `/v1/agent/self` on every Query; Pharos spends no extra request and never panics on an empty client list.
- A failed lookup is answered once, as an authoritative NOERROR with no records. CoreDNS also hands SERVFAIL back to the server after writing that Response; Pharos writes one Message.
- A name with no registrations, a registration with an unparsable address, or a QTYPE other than A, AAAA and SRV is answered NXDOMAIN with the SOA in the ANSWER section, exactly as CoreDNS does. Records added before the failing registration stay in the Response.
- The Query name must be under the Plugin zone (RFC 1034 §3.1); CoreDNS only drops as many trailing labels as the zone has. Names at or above the zone, with fewer than two labels below it, or not in class IN or ANY go to the next Plugin. `a.b.<zone>` is service `a` in namespace `b`; labels further down are ignored.
- Service, namespace, filter and region are percent-encoded as Go's `net/url` does. Escaped dots and other presentation escapes in a Query label reach Nomad as the raw byte, not as CoreDNS's escaped text.
- Each Query asks Nomad: there is no cache. A request ends after 5 seconds, an HTTP redirect is an error, only status 200 counts, replies are capped at 8 MiB, and compression is not requested. Connections are kept alive and reused (up to 8 idle per endpoint, not aged out).
- A registration port is truncated to 16 bits as Go's `uint16(Port)` does. An SRV target is not name-compressed (RFC 2782).
- Ready: the Plugin reports to the `ready` Plugin. With one address it is always ready and never probes, as in CoreDNS. With several it is ready once one of them answers `GET /v1/agent/self` with status 200 and a JSON body. CoreDNS probes on every `/ready` request; Pharos keeps a cached flag that a background task refreshes every 5 seconds, starting at Startup (the first probe is not awaited, so Startup and Queries never wait for Nomad, and the Plugin is not ready until it finishes). Restart and Shutdown stop the task. Query outcomes do not change the flag.
- Metrics `pharos_nomad_success_requests_total{namespace,server}` and `pharos_nomad_failed_requests_total{namespace,server}` replace the `coredns_` series and keep CoreDNS's help text. Success counts a Response whose lookup succeeded and that is not NXDOMAIN, so an empty NOERROR A or AAAA Response (the registrations only have the other address family) is a success too; a failed lookup, a service without registrations, an unsupported QTYPE and a registration with an unusable address count as failed. Queries handed to the next Plugin count as neither. CoreDNS counts after the write succeeds; Pharos counts when the Response is built. `server` is `dns://:PORT` (or `dns://IP:PORT` for a bound address) whatever the Transport, as for the other Plugins.
- The `namespace` label is a label of the Query name, so a client could create series without limit. Pharos keeps 64 distinct values per `server`; later ones are counted under `_other` (a Nomad namespace cannot contain `_`; a Query namespace spelled `_other` is counted there too, so no two series share labels). Labels are written in presentation form (RFC 4343 §2.1). CoreDNS has no bound.
- CoreDNS returns the error of the NXDOMAIN path with the Response, so the `errors` Plugin logs it; the Pharos Chain cannot carry an error and a Response together, so that error is not logged. A failed lookup logs a `WARN` line with the status or I/O error only (never the token, credentials or response text; a body that is not valid JSON is reported by line and column).
- A service name that is `.` or `..` is sent as is, because Go's `url.PathEscape` does not escape dots; Nomad cannot answer it as a service, so the lookup fails (empty NOERROR). Every other byte outside `A-Za-z0-9-_.~$&+=:@` is percent-encoded in the path, and outside `A-Za-z0-9-_.~` in the query, so a label cannot add a path segment, query parameter or header.
- Allocations: a warm Query allocates nothing of its own. The request target, the reply body and the decoded registrations live in a pool of buffers (up to 64, each kept only while the target is at most 4 KiB, the body 64 KiB and the registrations 1,024), so what a lookup allocates is hyper's, http's and tokio's (`tests/allocations/nomad_allocations.rs` pins Pharos at the allocation count of a bare hyper request to a stub, for A and SRV, with an escaped tag in the body). Still allocating: the first lookups, which grow a buffer; a burst with more than 64 lookups in flight, whose extra buffers are freed on return and built again later; a reply bigger than those limits, whose buffer is freed instead of kept; a new connection (TCP or TLS handshake, `ServerName`); `serde_json`'s own scratch buffer when a registration key or `Address` contains a JSON escape (an escaped value in any other field, such as Go's `\u0026` in a tag, is skipped without allocating); and every failure path (the error and its `WARN` line). The Plugin keeps no cache, so put the `cache` Plugin in front, as the CoreDNS README does.
- The Plugin follows `plugin.cfg` order: it runs after `whoami`, `file`, `forward` and the other Plugins that answer or end a Query first, as in CoreDNS.
- Differential scenarios are skipped: the harness starts a fixture only for the `kubernetes-*` scenarios, and a Nomad scenario needs a fake Nomad API that CoreDNS and Pharos share (a new fixture binary and Corefile templating in `xtask`). The behaviour is pinned by the ported `nomad_test.go` and `setup_test.go` cases, the unit tests in this folder and `tests/functional/nomad.rs`, which builds Corefiles through `configure` and `servers` against a local stub.
- Deferred: `NOMAD_SKIP_VERIFY` and `NOMAD_CAPATH` (setup fails), `NOMAD_NAMESPACE` (ignored), credentials inside an address and an address path (both refused at setup), idle-connection aging, and a Nomad response cache (use `cache`).
- Not replicated from CoreDNS: its second SERVFAIL packet after a failed lookup, and its out-of-range panic when no client was ever selected.
