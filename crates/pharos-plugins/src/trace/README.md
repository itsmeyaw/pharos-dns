# trace

[CoreDNS v1.15.0 README](https://github.com/coredns/coredns/blob/v1.15.0/plugin/trace/README.md)

## trace

- Pharos exports Zipkin v2 JSON over HTTP(S) from its own client rather than the OpenTracing/zipkin-go stack. Collector URL handling accepts `http://` and `https://` (case-insensitive scheme); URLs with userinfo are rejected.
- A bare Zipkin endpoint `host:port` becomes `http://host:port/api/v2/spans`, as in CoreDNS. A single positional argument is always an endpoint, never a type, so `trace datadog` names a Zipkin collector host called `datadog`.
- Sampling is `every N`: the Nth, 2Nth, ... Query is traced and `every 0` traces none, as in CoreDNS. The unsampled path costs one atomic increment and allocates nothing; `trace` also costs nothing per Query when not configured.
- Export never blocks a Query. Spans go to a bounded queue (`zipkin_max_backlog_size`, default 1000) that disposes the oldest span when full; a background task sends batches (`zipkin_max_batch_size` 100, `zipkin_max_batch_interval` 1s) with a 5s request timeout and no retry. Pharos counts outcomes, for both endpoint types, in `pharos_trace_exported_spans_total` and `pharos_trace_dropped_spans_total{reason="queue_full"|"export_failed"}`; CoreDNS exports no trace metrics. A collector outage logs one line, not one per batch.
- Shutdown and Restart flush queued spans (bounded by the request timeout); a failed Reload restores the exporter. If a stuck collector outlasts that timeout the exporter task is aborted and every span it discards is counted in `pharos_trace_dropped_spans_total{reason="export_failed"}`. A Query still in flight when the exporter stops is not recorded (CoreDNS does not flush on shutdown at all).
- `client_server` is parsed and validated as in CoreDNS but has no effect: it only shares one span between client and server when there is a parent span, and Pharos does not read an incoming parent span (the same limitation as the deferred DoH B3 extraction below).
- A zero or negative `zipkin_max_backlog_size` or `zipkin_max_batch_size` is accepted and silently replaced by the default (1000 and 100), as zipkin-go's reporter options do; a zero or negative `zipkin_max_batch_interval` (a negative duration parses and is clamped to zero) likewise keeps the 1s default.
- The sampled path takes a short `std` Mutex only to push the span into a `VecDeque`: no I/O or `.await` under the lock, and when the queue is full the oldest span is disposed of and counted.
- Zipkin trace IDs are 64-bit (16 hex digits; see below for Datadog), published as `trace/traceid` Metadata only when the metadata Plugin is active. Every Query starts a root span: Pharos does not read an incoming parent span, including the B3 header of a DoH request, so spans of a distributed trace are not linked.
- Spans carry `coredns.io/{name,type,rcode,proto,remote}` tags. With no Response written the returned status is the `rcode`; a Plugin error also gets the `error` tag and `event:error`/`error:<text>` annotations, as zipkin-go-opentracing does for log fields.
- The `datadog` endpoint type sends MessagePack to the Datadog agent trace API with a hand-written encoder rather than dd-trace-go v2. Each batch is one `POST /v0.4/traces` (dd-trace-go v2.10.1's method; the agent also accepts `PUT`) with `Content-Type: application/msgpack`, `Datadog-Meta-Lang: rust`, `Datadog-Meta-Lang-Interpreter`, `Datadog-Meta-Tracer-Version`, `X-Datadog-Trace-Count` and `Datadog-Client-Computed-Top-Level: t`. Each sampled Query is a one-span trace.
- The Datadog ENDPOINT is `host[:port]` (sent over `http://`) or an `http(s)://` base URL, to which `/v0.4/traces` is appended; the default is `localhost:8126`. Like dd-trace-go's `WithAgentAddr`, a bare `localhost` means port 80, not 8126. CoreDNS passes the endpoint to `WithAgentAddr` unchanged, so `http://localhost:8127` cannot work there but does in Pharos.
- Datadog spans are named and keyed like CoreDNS's: name and resource `servedns`, service from `service`, tags `coredns.io@{name,type,rcode,proto,remote}`, and for a Plugin error `error.message`, `error.type=dns_error` and `error=1`. CoreDNS's global tag `ext.SpanTypeDNS=true` is the key `dns` with value `true` (so no span type is set); Pharos also sets the span `type` to `dns`, which is what that tag aims at.
- `datadog_analytics_rate` is written as the span metric `_dd1.sr.eausr` when greater than 0. In CoreDNS v1.15.0 it only sets dd-trace-go's global analytics rate, which the core tracer never applies to its own spans, so there the option has no visible effect.
- Datadog trace IDs follow dd-trace-go v2's default 128-bit IDs: `trace_id` on the wire is the 64-bit span ID, `_dd.p.tid` carries the upper word (start second in the high 32 bits, then 32 zero bits), and `trace/traceid` Metadata is the 32-digit hex of both, as `Span.Context().TraceID()` returns. Span IDs are positive 63-bit integers. Zipkin keeps 16-digit IDs.
- Pharos sets `_sampling_priority_v1=1`, `_dd.top_level=1` and `process_id` on each Datadog span but does not implement agent sampling-rate feedback, `_dd.p.dm`, runtime metrics, client-side stats or `DD_*` environment configuration. `zipkin_max_*` settings do not apply to Datadog, as in CoreDNS; it uses the same 100-span batch, 1s interval and 1000-span backlog as the Zipkin path, and the agent request has the same 5s timeout and no retry.
- Not covered by the differential harness: spans go to a collector the harness cannot observe. Loopback stub collector tests cover the wire format.
- The service endpoint's host is resolved once at Startup (first IPv4 and IPv6 address), as zipkin-go does; its port comes from the first key of the Server block (shortcut for multi-port blocks).
